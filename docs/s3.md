# S3 payloads, local coordination, and offline transfer

S07 is implemented and undergoing qualification. This guide is for applications
configuring remote payload storage while keeping their SQLite catalog local.
On September 16, 2026, the user amended acceptance to permit a real Docker-local
RustFS or Garage S3-compatible service. Passing on a named compatible service
does not establish AWS S3 qualification or AWS certification. AWS-specific
evidence is deferred. Final test totals and S07 CI status belong in the
[forthcoming verification record](s07-verification.md).

## One host owns the catalog and coordination

All participating processes must share one local catalog and the same persistent
`coordination_directory` on one host. Use local filesystems suitable for the
[SQLite access protocol](sqlite.md). S3 stores payloads; it does not supply
distributed leases, a shared multi-host catalog, or online failover. Direct SQL
consumers must honor the [cooperative access protocol](lifecycle.md), and external
object writers must not mutate this store's private prefix.

`S3Storage` initialization performs filesystem and network I/O. A new store
requires an existing bucket and an empty, dedicated prefix. It creates a local
`meldstore-s3.json` marker and a remote `meldstore-storage.json` marker beneath
the prefix. The local marker binds the exact endpoint, bucket, prefix, logical
storage ID, and a coordinator ID derived from the canonical local path. Reopen
with the original directory and location spelling. Copying the marker to another
path, losing the local marker, or pointing a new coordinator at an existing
remote marker does not adopt the store. Missing/mismatched markers and uncertain
initialization fail closed; artifacts remain for inspection, not automatic repair.

## Explicit configuration

Create the disposable bucket separately. For a loopback RustFS service, provide
credentials to the application process and use canonical obstore keys:

```python
import os
from meldstore import BlobSchema, Catalog, S3Storage, Store, Text

s3_options = {
    "bucket": "meldstore-s07",
    "prefix": "qualification/run-001",
    "config": {
        "endpoint": "http://127.0.0.1:9000",
        "region": "us-east-1",
        "access_key_id": os.environ["RUSTFS_ACCESS_KEY"],
        "secret_access_key": os.environ["RUSTFS_SECRET_KEY"],
        "virtual_hosted_style_request": "false",
    },
    "client_options": {"allow_http": True},
}
schema = BlobSchema("dataset", {"title": Text(required=True)})
storage = S3Storage(coordination_directory="s3-coordination", **s3_options)
with Catalog("catalog.sqlite", adapter="sqlite") as catalog:
    store = Store(catalog, storage)
    store.install_schema(schema)
    record = store.import_file(
        "existing.parquet", schema=schema, metadata={"title": "example"}, id="sample"
    )
    with store.materialize(record["id"]) as verified_path:
        print(verified_path)  # Consume this temporary file inside the context.
```

The prefix is nonempty and consists of slash-separated segments containing only
letters, digits, `.`, `_`, and `-`; empty segments and `.`/`..` segments are
rejected. Do not add leading/trailing slashes. The endpoint must be an explicit
HTTP(S) URL without embedded credentials, query, or fragment. A conflicting
config bucket is rejected. Use canonical keys such as `endpoint`, not `aws_*`
aliases. `copy_if_not_exists="multipart"` and `conditional_put="etag"` are
enforced automatically; conflicting values fail validation.

Credentials and optional `credential_provider`, `retry_config`, and
`client_options` remain runtime inputs. MeldStore does not persist credentials
in the catalog, identity markers, backup manifest, or transfer result. Supply
them again when reopening; do not place secrets in endpoint URLs. The example's
HTTP setting is for loopback qualification, not a general remote deployment.

## Upload, verification, and disk space

`prepare_file`/`import_file` make a private local snapshot and hash its closed
bytes. Nonempty snapshots upload to fresh `staging/<uuid>` keys using multipart
PUT with 5 MiB chunks and maximum concurrency two per blob. A server-side
create-only copy publishes to `objects/<uuid>` using UploadPartCopy followed by
conditional CompleteMultipartUpload. Staging is deleted only after copy success.
This is not an S3 rename or a HEAD-then-overwrite protocol. A zero-byte payload
uses a direct conditional create-only PUT without multipart copy.

The backend must enforce destination exclusion, including competing copies to
the same key. A generic S3 compatibility claim is insufficient; conditional
completion, part copy, and race behavior need executable qualification on the
selected version. See the [backend evaluation](s07-backend-evaluation.md).

`materialize` downloads to a temporary file and verifies byte size and XXH3-128
before yielding it. ETags are not content digests. `stat`/`find` remain SQL-only;
object I/O happens outside long-lived SQL write transactions. Existing sources
remain unchanged. Handler serialization/deserialization retains its own memory
requirements; file streaming does not make a decoded dataframe bounded-memory.

Budget local temporary space for whole-blob snapshots and materializations.
`staging_directory` selects their temporary directory, which must already exist.
Multipart chunk/concurrency settings are per upload, not a global process-memory
cap. Multiple calls and client buffers add overhead. Transfer additionally uses
a complete local backup in the system temporary directory, plus per-blob work
space; it is not diskless remote-to-remote copying.

## Failures and cleanup

A failed upload can leave a completed staging object, a final orphan, or an
incomplete multipart upload. A lost completion response is an uncertain outcome;
do not overwrite or delete the destination to retry. Use the existing prepared
token, caller-ID resolution, reconciliation, and pending-deletion rules from
the [lifecycle guide](lifecycle.md). Resolve uncertain catalog outcomes before
destructive cleanup.

Exclusive maintenance can inventory completed objects and explicitly queue
orphan `objects/<uuid>` or `staging/<uuid>` keys. Cleanup does not delete identity
markers or arbitrary keys. Incomplete MPUs are absent from ordinary object
listing: MeldStore reconciliation/cleanup does not enumerate or abort them.
Use external S3 ListMultipartUploads/ListParts/AbortMultipartUpload tooling or
an appropriate backend lifecycle policy, scoped to the disposable/private
destination after writers are quiescent. Retry configuration does not guarantee
that abandoned uploads disappear.

## Offline backup, restore, and transfer

Close readers, writers, and direct SQL participants before opening
`Catalog(..., maintenance=True)`. Resolve prepared/publication operations,
pending cleanup, and metadata migrations first. The same one-logical-storage
restriction and application declaration from the [backup guide](backup.md)
apply to remote payloads.

| API | Destination and behavior |
| --- | --- |
| `store.backup(destination, application=...)` | Fresh local backup directory, including verified downloads of S3 payloads; manifest written last |
| `restore_backup(source, destination)` | Trusted local backup to fresh local catalog and payload root |
| `restore_backup_to_s3(source, destination, **s3_options)` | Trusted local backup to fresh local catalog/coordinator and empty remote prefix |
| `store.transfer(destination, application=...)` | Offline copy from local or S3 storage to a fresh local catalog/root via a temporary local backup |
| `store.transfer_to_s3(destination, application=..., **s3_options)` | Offline copy to a fresh local catalog/coordinator and empty remote prefix via a temporary local backup |

For example, with `s3_options` configured as above but using a **new empty
destination prefix**, transfer a local store:

```python
from meldstore import Catalog, LocalStorage, Store

with Catalog("source.sqlite", maintenance=True) as catalog:
    source = Store(catalog, LocalStorage("source-objects"))
    result = source.transfer_to_s3(
        "relocated/run-001",  # Parent exists; this directory must not exist.
        application={"id": "dataset-app", "schema_revision": "1"},
        **s3_options,
    )

with Catalog(result["catalog"]) as catalog:
    destination = Store(
        catalog, S3Storage(coordination_directory=result["storage"], **s3_options)
    )
    # Verify application queries before explicitly switching consumers.
```

Restore/transfer owns the destination coordinator and identity: do not pass
`coordination_directory`, `_storage_id`, or `_fresh` in its S3 options. The
returned `storage` is the local coordination path, not a local payload root or
an S3 URL. The result also includes `catalog` and `application`; retain the
explicit remote configuration separately for reopening.

Every referenced ready payload is verified at source and destination before the
destination catalog is published last. Public IDs, relative object keys, logical
storage ID, metadata, application SQL relationships, and source data are
preserved. Destination coordination is newly bound to its local path. There is
no automatic cutover or source deletion; prevent the copies from becoming
independent active writers accidentally.

Failures retain destination evidence for inspection. Retry with a fresh local
destination and fresh remote prefix; do not adopt a partial destination. A
successful S3-to-local backup is a portable local artifact and can be restored
without adopting the original S3 coordinator. These operational contracts do not
establish multi-host consistency, power-loss durability, or AWS qualification.
